# 0.9.0 Implementation Audit

- Status: Current implementation audit
- Scope: Product specification acceptance items 1 through 56

## Verdict

Every acceptance item currently declared in `docs/product/02-spec.md` has an
implemented source path and maintained executable evidence. No accepted MVP
item is documentation-only.

This does not mean every idea mentioned in the repository is implemented.
Post-MVP integrations and host-owned runtime concerns remain deliberately
outside the completion claim described below.

and real provider trials remain separate because they require an external
registry, a Docker daemon, or provider access.

## Deliberately Unimplemented

The following are not missing acceptance work:

- IDE and language-server integration;
- watch mode and persistent or cross-run compiler caching;
- cloud processing, telemetry, and hosted services;
- autofix, inline suppression, and generic plugin lifecycles;
- framework transforms, interpolation evaluation, producer discovery, and
  general dynamic-template support;
- authentication, CSRF policy, sessions, persistence, and deployment in the
  reference runtime; and
- public repair-rate claims without repeated controlled provider evidence.

These boundaries remain deferred or host-owned in the product specification,
project invariants, CLI contract, and monorepo boundaries. Implementing them
would require a new measured use case and an explicit product or architecture
decision; their absence does not make version `0.9.0` incomplete.

## Remaining Evidence Limits

- A passing static check proves only the configured inspection domains. It does
  not prove application runtime semantics.
- The adoption probe contains two maintained projects and is not an external
  false-positive-rate study or framework compatibility matrix.
- Docker integration proves the tested local daemon path, not independent
  execution provenance.
- Provider observations without enforced workspace and process isolation stay
  exploratory and cannot support a public repair-rate claim.
- Registry smoke can validate only a version that has been published to npm;
  local package smoke owns pre-publication consumer evidence.

## Versioning Decision

This audit records existing behavior and evidence. It changes no package API,
schema, CLI behavior, diagnostic meaning, runtime behavior, or release artifact,
so it does not trigger a package version change.
